# Cloud report: b145 (the exported build crashed going down from the Canyon)

**Summary**
- **Not reproduced, B145 stays open.** Every way down from the Canyon was driven inside a **release export**: the round 12 build itself (`9f69524e`) and today's `feature/backlog`. Linux release runs headless and under xvfb (OpenGL): 17 descents to the road, 0 crashes, 0 runtime SCRIPT ERRORs. The Windows exe could not run here: wine 9.0 page-faults on any Godot 4.6 exe, even `--version`.
- **Most likely class, confirmed on the release template:** a typed call on null. In the editor it is a SCRIPT ERROR and the game goes on. In a release export it is a **segfault**. A probe `var t: Texture2D = load("res://no/such.png"); t.get_width()` exits 139 at once. B142 (null weapon texture) closed the game the same way. So B145 is most likely a null call on a path the drives did not take.
- **Logging added, so the next crash names its line (D702):** `project.godot` gets `application/run/flush_stdout_on_print=true` (release did not flush `godot.log`, so the last lines before a native crash were lost) and `debug/settings/gdscript/always_track_call_stacks=true` (release errors now carry a GDScript backtrace). `Game.load_room()` prints `🚪 Game: room swap A → B` and `… done, B in` around every swap.
- **Reproduction tool:** `Scripts/Tools/export_drive.sh <binary> cutscene|walk|fall|mash [xvfb]` plays a scenario inside an exported build. Templates ignore `--script`, so an `override.cfg` beside the binary adds the `Scripts/Tools/export_drive.gd` autoload. It prints `DRIVE t=…` steps and `DRIVE: DONE`.
- **D-ID text:** D702 below. **Q-ID:** none. **B rows fixed:** none (B145 open; the report adds what is ruled out).
- **Full suite:** SUITE: 1 FAIL (116/117). `verify_skill_screen` HUNG (killed at 180 s, 0 SCRIPT ERROR) under suite load; alone it is RESULT: ALL PASS in 9 s. It does not touch the room swap or the descent.

## D-ID text (for `figma_decision_register.md`)

| D702 | ROUTINE CALL | **Release builds keep a readable crash log** (B145; `cloud/b145`). A typed call on null is only an error in the editor but a native crash in a release export (B142, B145), and the release template neither flushed `godot.log` per line nor kept a GDScript call stack. `project.godot`: `application/run/flush_stdout_on_print=true` (every print reaches the file before a crash), `debug/settings/gdscript/always_track_call_stacks=true` (every error in a release build prints `GDScript backtrace … [0] func (file.gd:line)`). `Game.load_room()` prints `🚪 Game: room swap <old> → <new>` before the swap and `🚪 Game: room swap done, <new> in` after it. Cost: a small per-call overhead in the GDScript VM and a flush per print; keep both until the playtest builds stop crashing. Exported builds are driven with `Scripts/Tools/export_drive.sh` (an `override.cfg` autoload; templates ignore `--script`). |

## 3. Export-only causes, checked

- **Resources missing from the pck:** every `"res://…"` literal in `.gd/.json/.tres/.tscn/.dqd/.cfg` was checked against the export's `Storing File` list (4425 files, with `.import` / `.remap`). Nothing on the Canyon → DesertRoad path is missing. The gaps that exist:
  - `enemy_variety.json`: the 7 big-kind scenes and sheets are not in the repo either. `EnemyVariety.available()` (D681) keeps them off.
  - `items.json` `release/assets/…` icons: known issue 6.
  - `Scenes/Menus/Game/{right_panel_component,sub_location_selection,timer_panel}.tscn` reference deleted scripts. Nothing loads those scenes; the export logs `Failed loading resource` for them.
- **`FileAccess` on imported files** (false in an export, since only `.import` / `.ctex` ship): only `ItemDatabase.gd:262` (icons, issue 6) and `Canyon.gd:467` (`.dqd`, shipped raw by `include_filter`) do this. Neither is a crash.
- **`DirAccess` listing res://:** none at runtime.
- **`assert()` with a side effect** (asserts are stripped in release): none. The `RoomPreloader` asserts only check values already computed.
- **Big textures:** the largest on the path is `DesertRoad_Terrain.png` at 3606×320. Every texture is uncompressed (mode 0) with no mipmaps.
- **Diff of the descent-path files between the played build and today** (`e9b9772f..HEAD`: Game.gd, DefaultEnemy, EnemySpawnPoint, RoomEnemySpawner, Player*, WeaponView, DesertRoad.tscn): no change looks like a crash fix. The big-kind guard (`efd13555`) came after the jackal_cursed sheet, which arrived after the playtest.

## 4. What is ruled out, and what is left

Ruled out:
- an export packaging gap on this path;
- a fall/walk exit down (there is none);
- the descent cutscene itself, the walk from the village, and key mashing through it, both builds, on the Linux release template;
- the first DesertRoad fights and the vulture;
- the hero dying there.

Left:
1. **A null typed call on a branch the drives did not take**, in the B142 class. The hero's real gear, skills or charms, an open inventory or journal mid-cutscene, a save loaded mid-route, Alt-Tab or a window resize during the fade.
2. **Windows-only engine/driver code:** D3D12 or Vulkan Forward+ on Sapega's GPU, against OpenGL/llvmpipe here.

The next crash log will say which.
