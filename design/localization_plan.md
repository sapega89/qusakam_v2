## 1. Rules

| Rule | What it means |
|---|---|
| Two locales | `en`, `uk`. `en` is the default (D121, English first). |
| No Cyrillic in `en` | Nothing the player sees in English carries a Cyrillic letter. |
| No English in `uk` | Every Latin word in Ukrainian is a key / button name: Tab, Esc, Enter, Space, the bound keyboard keys, A/B/X/Y, LB/RB/LT/RT, L3/R3, LS/RS, Start/Back/Guide, L/R (shop/craft bottom bar); or HP / SP / XP. Mouse buttons, sticks and the D-pad **are** translated (ЛКМ, лівий стік, хрестовина вгору). |
| Tabs | Tab names are text, translated (Інвентар, Спорядження, Мапа світу, Інше, Журнал, Навички, Стан). |
| Language names | Each in the current language: `English · Ukrainian` / `Англійська · Українська` (agent call, the strict reading of the rule — see the report's D-text 3). |

## 2. Mechanism (built in part 1)

- **Key = the English text** (gettext msgid). Scenes and code keep writing English (D121). Godot's
  `Label` / `Button` / `RichTextLabel` / tooltips / `PopupMenu` translate their own `text` (auto-translate),
  so a literal set straight on a control needs **no code change** — only a `uk.po` entry.
  Composed text (`"Lv %d" % n`, `"Requires: " + list`) goes through `tr("Lv %d") % n` (static funcs:
  `TranslationServer.translate`). Key-name labels set `auto_translate_mode = DISABLED` (the pad button
  "Back" must not become «Назад»).
- **Files:** `SampleProject/Resources/Translations/uk.po` is the source of truth (sections per screen);
  `en.po` has the same keys with value = key, regenerated by `python3 Scripts/Tools/po_sync.py`
  (it also fails on an empty or duplicate translation). `.po` over CSV: one file per locale, comments
  per section, plural support if ever needed, diff-friendly.
- **Registration without `project.godot`** (D270 pattern): `LocalizationManager._register_translations()`
  loads every `<lang>.po` and `TranslationServer.add_translation()`s it; a missing file is an assert, not a
  silent English. `export_presets.cfg` include filter gained `*.po` so exports carry them. When
  Sapega commits `project.godot`, the files may move to `internationalization/locale/translations` and the
  loop goes — `verify_locale` [0] asserts they are **not** there yet.
- **Applying the saved language:** `SettingsModule.apply_settings()` → `LocalizationManager.apply_language()`
  (the slot settings load deferred, after the autoload's `_ready`). `set_language()` = apply + save.
- **Language switch:** Settings → Game → Language — the existing segment row (`options_component.gd:337`),
  mouse / Enter / pad A; the list rebuilds, tab buttons and every visible label re-translate at once
  (`NOTIFICATION_TRANSLATION_CHANGED`). A notification composed in the old language re-renders
  (`CompanionJoinedNotification._notification`).

## 4. Part 2 — how data and dialogue get both languages

- **Data JSON:** same key scheme — the English field stays the key, the Ukrainian goes into `uk.po`
  (a section per file). Most data reaches the screen through a `Label` and translates on its own; the
  composers that glue data into a sentence need `tr()` on the data part (`crafting_service.gd` "%d %s",
  `enchanting_service.gd` "%s ×%d → %s", `skills_component.gd` `_detail_kind`, inventory hints, the
  `"%s · %s"` joins). Delete the stale `name_ru` / `description_ru` fields and the `language` params in
  `ItemDatabase.get_item_name()/get_item_description()` (Russian, unused).
  Tooling: extend `po_sync.py` (or a sibling) to list every JSON text field missing from `uk.po`.
- **Character names:** give every speaker an id (`ALISIA`, `ASTRIT`, `URIZEN`, `MERCHANT`, `ENEMY`) in
  `.dqd`; the display name comes from `journal_people.json` `title` (English key, `uk.po` value);
  `CharacterManager` / `CompanionManager.NAMES` switch to English keys (Kusakam, Alisia, Astrit, Urizen —
  the code ids already spell them so). Tests that compare `"Кусакам"` (`verify_status`, `verify_party_panel`,
  `verify_dialogue_speaker`, `verify_companions`) change with it.
- **Dialogue (`.dqd`) — per-locale files** (agent call, D-text 5 in the report): the Ukrainian files stay
  where they are (`dialogue_quest/<id>.dqd` — Sapega writes in Ukrainian); the English twin is
  `dialogue_quest/en/<id>.dqd` with the same structure. One resolver picks the file by locale — today
  12 places in 11 files build `"res://dialogue_quest/%s.dqd"` (`StateChangeTrigger.gd:202`, `RelicArmor.gd:38`,
  `LaboratoryOutside.gd:83`, `DesertRoad.gd:108`, `Village.gd:224`, `CityGates.gd:132`, `Canyon.gd:461,472`,
  `Laboratory.gd:114`, `StoryNpc.gd:31`, `NpcBase.gd:185`, `Cutscene.gd:65`) — replace them with one
  `DialoguePaths.of(id)`. A verify checks every Ukrainian file has an English twin with the same
  number of `say`/`exit` lines and the same speaker ids. Why not keys in `.po`: dialogue is authored
  prose in Ukrainian; Ukrainian msgids would break the English-key rule, and a translator works
  better on a whole scene than on loose lines.
- **verify_locale:** set `DATA_DEFERRED := false` (`verify_locale.gd:27`) and delete `RUNTIME_FILLED`
  (`:32`) — then every data string, speaker name and dialogue line is checked like the UI. Add a walk
  that plays one line of each `.dqd` in both locales (dialogue box text + speaker name).
