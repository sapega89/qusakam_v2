## 🎯 Архітектурні принципи

### Component-Based Architecture

- Компоненти створюються в сценах (.tscn), а не в скриптах
- Кожен компонент має чітку відповідальність
- Компоненти можна повторно використовувати в різних сценах

### Interface Segregation Principle

- ISceneStateManager забезпечує уніфікований доступ
- Компоненти реалізують інтерфейс через методи
- Безпечні методи для роботи з компонентами

### Single Responsibility Principle

- SceneStateManager - тільки управління стейтами
- DialogueStateTrigger - тільки інтеграція діалогів зі стейтами
- CanyonStateManager - тільки логіка стейтів для Canyon

## 📊 Переваги нової архітектури

### Порівняння зі старою архітектурою

| Аспект | Старий підхід (Canyon.gd) | Новий підхід (Компоненти) |
|--------|---------------------------|---------------------------|
| Логіка стейтів | В скрипті | В компонентах сцени |
| Діалоги | Через `_play_dialogue()` | Через DialogueStateTrigger |
| Зміна стейту | Вручну через `current_state =` | Автоматично після діалогу |
| Тестування | Складно (залежності) | Легко (ізольовані компоненти) |
| Повторне використання | Неможливо | Можливо (DialogueStateTrigger) |
| Візуальна настройка | Немає | Так (в Inspector) |

### Переваги

1. **Розділення відповідальностей**: Кожен компонент має одну відповідальність
2. **Повторне використання**: DialogueStateTrigger можна використовувати в будь-якій сцені
3. **Легке тестування**: Компоненти можна тестувати окремо
4. **Візуальна настройка**: Всі параметри налаштовуються в редакторі
5. **Інтерфейси**: Уніфікований доступ через ISceneStateManager
6. **Чистий код**: Дотримується SOLID принципів
